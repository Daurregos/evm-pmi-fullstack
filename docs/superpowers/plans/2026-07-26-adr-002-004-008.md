# ADR-002, ADR-004 and ADR-008 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Document the approved persistence, non-evaluable API semantics, and aggregate lifecycle decisions in three accepted ADRs of at most 400 words each.

**Architecture:** ADR-002 keeps captured state authoritative and derived EVM output transient under ADR-001. ADR-004 assigns `null` one exclusive business meaning while leaving response shape and the evaluable values' external type and format to ADR-006. ADR-008 enforces the Project–Activity composition atomically in persistence under the single-snapshot model of ADR-005.

**Tech Stack:** Markdown, Git, repository PRD and ADR conventions

The single decision sentence must establish that persistence keeps only project
and activity source data, while the ADR-001 module derives EVM indicators,
interpretations and consolidated results without persisting them. Context must
make the five captured fields and the expected scale explicit. Compare
persisting every derived result with persisting only PV and EV; cover duplicated
state, synchronization, query convenience and the limited benefit at the
expected scale.

Consequences must state that captured data remain authoritative, rule changes
need no derived-data migration, on-demand materialization has an accepted cost,
and persistence-level filtering or ordering by derived indicators becomes
harder. Preserve the boundaries: ADR-007 decides when and in which flow to
calculate; ADR-006 decides REST names, grouping and general response shape.
Future verification must inspect persistence for the absence of all indicators,
interpretations and consolidations; integration tests must vary BAC, planned
progress, actual progress and AC, confirm that a name-only edit leaves derived
results unchanged, and confirm no operation writes calculated results.

- [ ] **Step 1: Create ADR-004 with the approved decision**

Create `docs/adr/004-contrato-api-indicadores-no-evaluables.md` as an accepted
ADR dated 2026-07-26, related to RF-05, RF-07, RF-08, PRD §§7.1–7.3 and §9,
and dependent exactly on ADR-003. Use the five required sections and no more
than 400 words.

The single decision sentence must establish that a successful API response
retains every derived indicator and uses `null` exclusively when the domain
declares that indicator non-evaluable, never as zero or as an error. Context
must distinguish legitimate zero results from undefined divisions and state
that ADR-003 fixes precision and presentation while ADR-006 owns the external
type and format of evaluable values. Compare omission, a tagged result carrying
status and value, and zero as a sentinel; cover variable structure, unnecessary
structure for the sole special case, and false zero semantics.

Consequences must reserve evaluable type and format plus names, grouping and
envelope to ADR-006; keep indicator presence stable; prohibit other meanings
for `null`; retain separate validation and infrastructure error channels; and
record conditional consumer handling as the cost. Future contract tests must
cover all five PRD §7.3 states and an empty project, `null` for non-evaluable
divisions, `CPI = 0` for `EV = 0` with `AC > 0`, `SPI = 0` for `EV = 0` with
`PV > 0`, stable indicator presence and successful responses. Include a case
where an activity CPI is non-evaluable but CPI calculated from consolidated
totals is evaluable.

- [ ] **Step 1: Create ADR-008 with the approved decision**

Create `docs/adr/008-ciclo-vida-borrado-cascada.md` as an accepted ADR dated
2026-07-26, related to RF-01, RF-02, PRD §5, the deletion assumption in §8 and
the limitations in §10, and dependent exactly on ADR-005. Use the five required
sections and no more than 400 words.

The single decision sentence must define Project–Activity as a persistence
composition: physical project deletion removes all activities atomically,
whereas deleting one activity preserves its project and siblings. Context must
trace the aggregate model and physical deletion to the PRD, history exclusion to
ADR-005, and recovery exclusion to PRD §10. Compare application-coordinated
deletion, blocking project deletion while activities exist, and soft deletion;
cover partial-state risk, the conflict with RF-01, and out-of-scope lifecycle
states.

Consequences must prohibit orphans, require complete rollback on failure,
acknowledge coupled lifecycles and irreversible loss as costs, require PRD and
ADR-005 review before adding audit, recovery or retention, and note under
ADR-002 that no persisted derived state needs cleanup. Future integration tests
must delete a project with several activities, verify absence and no orphans,
force a failure after deletion starts and verify that rollback leaves the
project and all its activities present, and delete one activity while
preserving the project and siblings. Model review must confirm that integrity
does not depend on manual consumer calls.
